# Офлайн-парсер на Windows

Разбор собранных обходом страниц (то же, что пункт 3 в `make parkrun` на Маке).
`make` и лончер — маковые, на Windows они не нужны: запускается сам скрипт.

Мак и Windows можно (и нужно) гонять **одновременно** — они не пересекаются,
см. раздел «Почему две машины не мешают друг другу».

## Установка (один раз)

1. **Python 3.10+** — с python.org, при установке галочка *Add python.exe to PATH*.
2. **Клон репозитория** (git уже есть):

   ```cmd
   git clone https://github.com/PopovDmitryA/parkrun-monitoring
   cd parkrun-monitoring
   ```

3. **Зависимости** (всё бинарными колёсами, компилятор не нужен):

   ```cmd
   py -m pip install -r athlete_sweep\requirements-parser.txt
   ```

## Запуск

```cmd
cd parkrun-monitoring
py -m athlete_sweep.file_parser --delete
```

Спросит SSH-хост, пользователя и пароль сервера — вводишь один раз за запуск
(пароль не отображается). Дальше сам: качает по SFTP собранные файлы, парсит,
пишет в БД, помечает очередь.

Чтобы не вводить креды каждый раз — задай переменные окружения в той же сессии:

```cmd
set PM_SSH_HOST=195.58.34.112
set PM_SSH_USER=viewer
set PM_SSH_PASS=пароль
py -m athlete_sweep.file_parser --delete
```

**Перед каждым запуском — `git pull`**: код меняется часто, а старая версия
может тихо работать не так (например, до 28.07 счётчик капч вообще не писался).

```cmd
cd parkrun-monitoring
git pull
```

### Ключи

| ключ | что делает |
|---|---|
| `--threads N` | сколько страниц обрабатывать параллельно (по умолчанию 1). **Главный рычаг скорости** |
| `--delete` | удалять файлы сырья с сервера после записи в БД. **Для постоянной работы нужен** — иначе диск сервера заполнится |
| `--limit N` | обработать N атлетов и выйти (0 = без предела, по умолчанию) |
| `--once` | разобрать что есть и выйти, не ждать новых |
| `--batch N` | сколько строк бронировать за раз (по умолчанию 50) |

### Сколько потоков ставить

Упирается не в процессор, а в ожидание сети — пока один поток ждёт файл с
сервера, остальные работают. Замер на Маке (канал через VPN): 1 поток — 13/мин,
**8 потоков — 119/мин (≈9x)**. Выше 8 прирост почти пропадает: все каналы идут
через одну ssh-сессию, она и становится узким местом.

- быстрый канал (как на этой винде) — начни с `--threads 8`;
- если хочется ещё — запусти **второй процесс** парсера, а не 32 потока в одном:
  у второго процесса будет своя ssh-сессия. Столкновений не будет (см. ниже).

```cmd
py -m athlete_sweep.file_parser --delete --threads 8
```

Остановка — `Ctrl+C`. Незавершённая бронь освободится сама через 15 минут.

## Почему две машины не мешают друг другу

Ничего настраивать не надо, защита уже в коде:

- **Бронь под блокировкой.** Парсер забирает пачку строк запросом
  `FOR UPDATE SKIP LOCKED` — Postgres физически не отдаст одну строку двум
  клиентам: второй пропустит занятые и возьмёт следующие.
- **Именная метка.** Каждый парсер пишет в `claimed_by` своё имя вида
  `parser:<имя-компьютера>:<pid>` — видно, кто что взял.
- **Аренда 15 минут.** Если машину выключили посреди пачки, её строки через
  15 минут заберёт другой парсер (`claimed_by LIKE 'parser:%'` + просроченный
  `claimed_at`). Ничего не теряется и не зависает.
- **Файлы не конфликтуют:** машины работают над разными атлетами, поэтому с
  `--delete` каждая удаляет только своё.

Так что смело запускай Мак и Windows вместе — суммарная скорость сложится.
Проверить, кто сейчас работает, можно на табло: плашка «обработка / час».

# Обход с решателем капчи (то же, что пункт 4 в `make parkrun`)

Второй сценарий для этой машины: не разбирать чужое сырьё, а **самому качать
атлетов** — своим каналом, со своим IP. Капчу скрипт проходит сам.

## Дополнительные зависимости (один раз)

Ставить **по одной команде**, по порядку:

```cmd
py -m pip install --upgrade pip
py -m pip install torch --index-url https://download.pytorch.org/whl/cpu
py -m pip install open_clip_torch playwright
py -m playwright install chromium
```

**Почему отдельный index-url для torch:** без него pip тянет сборку под видеокарту
(CUDA) — это ~2.5 ГБ, и на машине без нужных драйверов установка часто падает.
CPU-сборка весит ~200 МБ и нам её достаточно: модель маленькая, работает быстрее
секунды на девяти картинках.

Проверить, что встало:

```cmd
py -c "import torch, open_clip; print('torch', torch.__version__, 'OK')"
```

При ПЕРВОМ запуске решателя докачается сама модель (~350 МБ) — один раз, дальше
берётся из кеша.

## Запуск

```cmd
cd parkrun-monitoring
git pull
py -m athlete_sweep.waf_solver unused --fast --limit 0 --delay 2
```

Спросит SSH-креды сервера (нужны только для базы — тоннель поднимается один,
к `pm-postgres`). Страницы качаются **напрямую твоим каналом**, не через сервер.

| ключ | что делает |
|---|---|
| `--limit 0` | без предела, до `Ctrl+C` |
| `--delay 2` | пауза между атлетами; можно снижать до 0-1, следя за числом капч |
| `--exit-port 10859` | ходить через выход сервера, а не своим каналом (обычно НЕ нужно) |

Воркер появляется на табло /hq строкой `<имя-компьютера>-direct` и копит там
собранное, время работы и статистику капч.

## Чего ожидать

Замеры на Маке: 2.4–3.4 с на атлета, ~630-750 в час при задержке 2 с. Капчи
редки — одна на 25–53 атлета, решаются сами примерно за 25 секунд.

NB: на Windows этот сценарий пока не прогонялся — если что-то пойдёт не так,
покажи вывод целиком.
