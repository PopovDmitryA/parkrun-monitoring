# Офлайн-парсер на Windows

Разбор собранных обходом страниц (то же, что пункт 3 в `make parkrun` на Маке).
`make` и лончер — маковые, на Windows они не нужны: запускается сам скрипт.

Мак и Windows можно (и нужно) гонять **одновременно** — они не пересекаются,
см. раздел «Почему две машины не мешают друг другу».

## Установка (один раз)

1. **Python 3.10+** — с python.org, при установке галочка *Add python.exe to PATH*.
2. **Клон репозитория** (git уже есть):

   ```cmd
   git clone https://github.com/PopovDmitryA/parkrun-monitoring
   cd parkrun-monitoring
   ```

3. **Зависимости** (всё бинарными колёсами, компилятор не нужен):

   ```cmd
   py -m pip install -r athlete_sweep\requirements-parser.txt
   ```

## Запуск

```cmd
cd parkrun-monitoring
py -m athlete_sweep.file_parser --delete
```

Спросит SSH-хост, пользователя и пароль сервера — вводишь один раз за запуск
(пароль не отображается). Дальше сам: качает по SFTP собранные файлы, парсит,
пишет в БД, помечает очередь.

Чтобы не вводить креды каждый раз — задай переменные окружения в той же сессии:

```cmd
set PM_SSH_HOST=195.58.34.112
set PM_SSH_USER=viewer
set PM_SSH_PASS=пароль
py -m athlete_sweep.file_parser --delete
```

**Перед каждым запуском — `git pull`**: код меняется часто, а старая версия
может тихо работать не так (например, до 28.07 счётчик капч вообще не писался).

```cmd
cd parkrun-monitoring
git pull
```

### Ключи

| ключ | что делает |
|---|---|
| `--threads N` | сколько страниц обрабатывать параллельно (по умолчанию 1). **Главный рычаг скорости** |
| `--delete` | удалять файлы сырья с сервера после записи в БД. **Для постоянной работы нужен** — иначе диск сервера заполнится |
| `--limit N` | обработать N атлетов и выйти (0 = без предела, по умолчанию) |
| `--once` | разобрать что есть и выйти, не ждать новых |
| `--batch N` | сколько строк бронировать за раз (по умолчанию 50) |

### Сколько потоков ставить

Упирается не в процессор, а в ожидание сети — пока один поток ждёт файл с
сервера, остальные работают. Замер на Маке (канал через VPN): 1 поток — 13/мин,
**8 потоков — 119/мин (≈9x)**. Выше 8 прирост почти пропадает: все каналы идут
через одну ssh-сессию, она и становится узким местом.

- быстрый канал (как на этой винде) — начни с `--threads 8`;
- если хочется ещё — запусти **второй процесс** парсера, а не 32 потока в одном:
  у второго процесса будет своя ssh-сессия. Столкновений не будет (см. ниже).

```cmd
py -m athlete_sweep.file_parser --delete --threads 8
```

Остановка — `Ctrl+C`. Незавершённая бронь освободится сама через 15 минут.

## Почему две машины не мешают друг другу

Ничего настраивать не надо, защита уже в коде:

- **Бронь под блокировкой.** Парсер забирает пачку строк запросом
  `FOR UPDATE SKIP LOCKED` — Postgres физически не отдаст одну строку двум
  клиентам: второй пропустит занятые и возьмёт следующие.
- **Именная метка.** Каждый парсер пишет в `claimed_by` своё имя вида
  `parser:<имя-компьютера>:<pid>` — видно, кто что взял.
- **Аренда 15 минут.** Если машину выключили посреди пачки, её строки через
  15 минут заберёт другой парсер (`claimed_by LIKE 'parser:%'` + просроченный
  `claimed_at`). Ничего не теряется и не зависает.
- **Файлы не конфликтуют:** машины работают над разными атлетами, поэтому с
  `--delete` каждая удаляет только своё.

Так что смело запускай Мак и Windows вместе — суммарная скорость сложится.
Проверить, кто сейчас работает, можно на табло: плашка «обработка / час».

# Обход с решателем капчи (то же, что пункт 4 в `make parkrun`)

Второй сценарий для этой машины: не разбирать чужое сырьё, а **самому качать
атлетов** — своим каналом, со своим IP. Капчу скрипт проходит сам.

## Дополнительные зависимости (один раз)

Ставить **по одной команде**, по порядку:

```cmd
py -m pip install --upgrade pip
py -m pip install torch --index-url https://download.pytorch.org/whl/cpu
py -m pip install open_clip_torch playwright socksio
py -m playwright install chromium
```

`socksio` нужен, чтобы httpx ходил через SOCKS-прокси локального xray (см. ниже).

**Почему отдельный index-url для torch:** без него pip тянет сборку под видеокарту
(CUDA) — это ~2.5 ГБ, и на машине без нужных драйверов установка часто падает.
CPU-сборка весит ~200 МБ и нам её достаточно: модель маленькая, работает быстрее
секунды на девяти картинках.

Проверить, что встало:

```cmd
py -c "import torch, open_clip; print('torch', torch.__version__, 'OK')"
```

При ПЕРВОМ запуске решателя докачается сама модель (~350 МБ) — один раз, дальше
берётся из кеша.

## Запуск

```cmd
cd parkrun-monitoring
git pull
py -m athlete_sweep.waf_solver unused --fast --limit 0 --delay 2
```

Спросит SSH-креды сервера (нужны только для базы — тоннель поднимается один,
к `pm-postgres`). Страницы качаются **напрямую твоим каналом**, не через сервер.

| ключ | что делает |
|---|---|
| `--limit 0` | без предела, до `Ctrl+C` |
| `--delay 2` | пауза между атлетами; можно снижать до 0-1, следя за числом капч |
| `--proxy-file paid_proxies.txt` | список прокси; при старте спросит, каким пользоваться |
| `--proxy https://host:8444` | задать прокси напрямую (без вопроса) |
| `--exit-port 10859` | ходить через выход сервера, а не своим каналом |

Воркер появляется на табло /hq строкой `<имя-компьютера>-direct` (или `-<IP прокси>`)
и копит там собранное, время работы и статистику капч.

## Несколько прокси = несколько терминалов

Скрипт лёгкий на httpx, но браузер-решатель тяжёлый — **1–2 сессии на машину**,
не больше (иначе своп и зависание, проверено на Маке). Если решил гонять через
платные прокси в несколько окон — в каждом окне свой прокси:

```cmd
py -m athlete_sweep.waf_solver --fast --proxy-file paid_proxies.txt --limit 0 --delay 2
```

Спросит номер прокси — в каждом терминале выбираешь свой. Пересечений не будет:
атлеты берутся из очереди через `FOR UPDATE SKIP LOCKED`, на табло у каждого своя
строка по IP прокси.

**ВАЖНО про привязку IP.** Платные mcccx-прокси привязаны к IP сервера
`195.58.34.112`. С домашнего IP они, скорее всего, НЕ авторизуются — скрипт при
старте это проверит и скажет «прокси не отвечает». Тогда: перепривяжи прокси у
провайдера на IP этой машины, либо запускай их с сервера. Пока не авторизуют —
работать не будут, это не про скрипт.

## Чего ожидать

Замеры на Маке: 2.4–3.4 с на атлета, ~630-750 в час при задержке 2 с. Капчи
редки — одна на 25–53 атлета, решаются сами примерно за 25 секунд.

На Windows подтверждено: 4 окна одновременно держатся стабильно (~50% RAM
из 16 ГБ на снимках Task Manager), CPU скачет 3–65% — это нормально, пики
совпадают с одновременным решением капчи в нескольких окнах разом, не
повод для тревоги сам по себе.

## Автоперезапуск для безнадзорного прогона (недели/месяц)

Скрипту предстоит крутиться без присмотра долго. Два риска у этого:
Python/Chromium не всегда сразу отдают память ОС обратно — за долгий срок
рабочее множество памяти может подрасти (по двум замерам на живом прогоне
рост был ~800 МБ за 2.5 часа при 4 окнах — не доказанная утечка, скорее
нормальный разогрев, но проверять это гаданием на месячном прогоне не
стоит). И падения: сеть легла, тоннель не поднялся, необработанная
ошибка — без обёртки это требует, чтобы человек заметил и перезапустил
руками, а «без участия человека» тогда не получится.

`win_autorestart.cmd` закрывает оба риска одним и тем же механизмом: гоняет
решатель порциями (`--limit`, по умолчанию 3000 атлетов на цикл) и
перезапускает свежим процессом при любом завершении — по лимиту, по
краху, по чему угодно. Новый процесс = гарантированно чистая память,
свежий CLIP, ничего не накапливается.

```cmd
set PM_SSH_PASS=твой_пароль_сервера
win_autorestart.cmd 9 1 3000
```

Аргументы: номер прокси из `private_local.txt` (тот же, что скрипт обычно
спрашивает), задержка в секундах, необязательный размер цикла (по
умолчанию 3000 атлетов ≈ несколько часов работы при задержке 1с).

**`set PM_SSH_PASS` обязателен** для по-настоящему безнадзорного прогона —
без него на каждом перезапуске (каждые ~3000 атлетов) скрипт встанет и
будет ждать ввода пароля в консоли, и «месяц без участия человека» не
выйдет. Переменная живёт в рамках этого окна cmd и наследуется каждым
новым запуском автоматически.

Открой отдельное окно с этим скриптом на каждый выход — как обычно, свой
номер прокси в каждом.

# Приватные выходы нативно (локальный xray на винде)

Чтобы гнать приватные VPN-выходы БЕЗ сервера (путь Б). Файлы `xray_windows.json`
и `private_local.txt` тебе присланы отдельно (в них твои VPN-секреты — не выкладывай).

1. Скачай `xray.exe` — github.com/XTLS/Xray-core/releases → `Xray-windows-64.zip`.
2. Положи `xray.exe`, `xray_windows.json`, `private_local.txt` в одну папку.
3. **Окно 1** (держать открытым) — поднять все выходы локально:
   ```cmd
   xray.exe -c xray_windows.json
   ```
   Поднимет 14 локальных SOCKS5-портов 10851–10864, каждый — свой VLESS-выход.
4. **Окна 2–6** — по решателю на выход:
   ```cmd
   py -m athlete_sweep.waf_solver --fast --proxy-file private_local.txt --limit 0 --delay 2
   ```
   Выбираешь номер выхода. В каждом окне — свой.

ВАЖНО: инбаунды xray — **SOCKS5**, а не HTTP. С HTTP-прокси Playwright-Chromium на
винде падал `ERR_PROXY_CONNECTION_FAILED`; на SOCKS5 работает (проверено). Поэтому
`private_local.txt` содержит `socks5://…`, и httpx для этого требует `socksio`.

ВАЖНО про баны: эти VPN-аккаунты сейчас крутит серверный manager. Гнать те же
выходы ещё и с винды = двойной туннель = отлёжка. Скажи, когда винда поедет —
остановлю серверный manager, чтобы выходы освободились.
